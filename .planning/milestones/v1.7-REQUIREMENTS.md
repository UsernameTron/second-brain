## v1.8 Backlog (filed 2026-07-19, post-v1.7 promotion incident review)

Priority order is deliberate: P1 items are silent-failure or data-split risks in the live promotion workflow.

**[P1] v1.8 — PROMOTE-PARSE-01: Checkbox parser requires exactly `- [x]`; near-miss marks silently promote nothing while reporting success.** The accept matcher is `/^- \[x\] accept$/im` (`src/promote-memories.js:113`) — `- [ X] accept`, `- [X ] accept`, extra interior spacing, or a trailing space all parse as unreviewed (`checkboxStatus: null`), the candidate is skipped, and the run exits green with `promoted 0`. A human who reviewed the batch believes it shipped; nothing did, and no counter distinguishes "nothing eligible" from "eligible but unparseable." Observed 2026-07-19: a 40-candidate corpus with checked boxes returned all-zeros with no diagnostic. Fix: tolerate whitespace variants in the checkbox regex, or count near-miss checkbox lines and fail loudly when candidates carry unparseable marks.

**[P1] v1.8 — PROMOTE-VAULT-01: `VAULT_ROOT` binds at module load, splitting the proposals corpus across roots.** `src/memory-proposals.js:18` captures `process.env.VAULT_ROOT` into a module-level const at require time (unlike `promote-memories.js`, which resolves `VAULT_ROOT()` per call). Any process that requires the module with a different root — or sets the env var after require — stages candidates into that root's `proposals/memory-proposals.md`, invisibly forking the corpus. Observed 2026-07-19: an extraction run staged 40 candidates into the repo-root copy while the live vault copy promoted a parallel 54; three later sessions were misled by the fork. Fix: make VAULT_ROOT resolution call-time in memory-proposals.js (match the promote-memories.js pattern), and assert both modules agree on the resolved root at promotion start.

**[P2] v1.8 — PROMOTE-ID-01: Proposal IDs are not globally unique across proposal files.** `generateCandidateId()` (`src/memory-proposals.js:51-57`) derives the next `mem-YYYYMMDD-NNN` by scanning only the current proposals file for today's max NNN. Two proposal files (see PROMOTE-VAULT-01) or an archive-then-restage cycle mint colliding IDs — both corpora carried `mem-20260719-001` on 2026-07-19. IDs appear in `source-ref::`/audit trails, so collisions poison provenance. Fix: include a per-file or per-root discriminator in the ID, or scan the archive dir when computing the max.
